# Нагрузочный тест

Машина: 4 vCPU / 8 ГБ (Debian 13). Генератор нагрузки `hey` работал на той же машине, что и приложение с базой,
то есть отбирал у них CPU — на отдельном сервере цифры будут выше.

Данные: `seed_kg` + 3000 сгенерированных преподавателей и 30 000 отзывов (`seed_fake`, для main — тот же генератор).
gunicorn в обоих случаях: 9 процессов × 4 потока (gthread), PostgreSQL 16.

* **до** — ветка `main` (5149bdd), gunicorn напрямую, Postgres в Docker;
* **после** — `docker-compose.prod.yml` (web + Postgres + Redis), `DEBUG=False`.

Команда (60 секунд на каждую страницу):

```bash
hey -z 60s -c 50 -t 30 -H "Accept-Language: ru" -H "X-Forwarded-Proto: https" http://127.0.0.1:8000/
# то же для /schools/<вуз>/, /professors/<преподаватель>/, /?q=физика ; затем -c 200
```

| Страница | до, c=50: RPS / p50 / p95 / p99 / ошибки | после, c=50 | после, c=200 |
|---|---|---|---|
| Главная `/` | 1.7 / — / — / — / **100 %** таймауты (30 с) | 661 / 54 / 196 / 261 мс / 0 % | 629 / 266 / 786 / 1121 мс / 0 % |
| Вуз `/schools/…/` | 1.2 / 28 с / — / — / **90 %** | 544 / 76 / 213 / 261 мс / 0 % | 538 / 287 / 999 / 1313 мс / 0 % |
| Преподаватель | 51 / 550 / 1438 / 1644 мс / 1.2 % | 370 / 123 / 266 / 410 мс / 0 % | 376 / 421 / 1263 / 1579 мс / 0 % |
| Поиск `/?q=физика` | 1.9 / 13.5 с / 26 с / 30 с / **33 %** | 626 / 63 / 183 / 336 мс / 0 % | 589 / 287 / 816 / 977 мс / 0 % |

Почему было медленно: главная загружала всех преподавателей и для каждого делала ~6 SQL-запросов
(3000 × 6 = 18 000 запросов на одну страницу), пагинация делалась уже в Python.
